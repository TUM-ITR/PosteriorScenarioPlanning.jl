PosteriorScenarioPlanning — Module
module PosteriorScenarioPlanning

Tools for inference, optimal control, and planning with uncertain stochastic state-space models.

The package supports workflows in which posterior samples of model parameters and latent states are inferred from observed input-output data and then used as scenarios for control. It separates three layers:

  • Inference — draw posterior samples of parameters and latent states from data, typically via particle MCMC.
  • Optimal control (synthesis) — combine posterior samples as scenarios in an optimal-control problem (OCP), e.g. a robust or risk-sensitive formulation, and solve it once to obtain an input trajectory (solve_ocp!).
  • Planning (synthesis + certification) — wrap an OCP in a synthesis–validation loop that certifies each candidate input on a freshly drawn validation set and adaptively recalibrates the formulation until a robustness guarantee holds (plan!).

The module provides:

  • State-space model and data abstractions
  • Particle filtering for likelihood estimation and trajectory sampling
  • Particle marginal Metropolis–Hastings (PMMH) samplers
  • Adaptive MCMC mechanisms, such as step-size and particle-count adaptation
  • Diagnostics for assessing MCMC convergence and mixing
  • Trajectory cost and constraint abstractions
  • Posterior-sample-based OCP formulations
  • Solver interfaces for repeated OCP solves, such as in model predictive control (MPC)
  • Validation tools (violation counting and Clopper–Pearson bounds) and planners that certify a control law against a robustness level

A typical workflow is:

  1. Define a stochastic state-space model and observed data.
  2. Build an MCMC workspace and configure a sampler.
  3. Run particle MCMC to obtain posterior samples of parameters and latent states.
  4. Define a control problem through trajectory costs and constraints.
  5. Build an OCP workspace using posterior samples as scenarios.
  6. Solve the OCP directly (solve_ocp!) for an input trajectory, or run a planner (plan!) to obtain a certified input trajectory with an associated robustness guarantee.
  7. Update posterior samples or scenario data and repeat as needed (e.g. in a receding-horizon loop).

The implementation is organized into modular components for models, data, particle filtering, MCMC sampling, adaptation, diagnostics, optimal-control formulations, validation, planning, and solver backends.

PosteriorScenarioPlanning.DiscreteTimeStochasticSSM — Type
DiscreteTimeStochasticSSM <: AbstractModel

Discrete-time stochastic state-space model with parametric dynamics.

The model is defined by

\[\begin{aligned} x_{t+1} &= f(x_t, u_t, v_t, \theta), \\ y_t &= g(x_t, u_t, \theta) + w_t, \end{aligned}\]

where $x_t$ is the latent state, $u_t$ is the input, $v_t$ is the process noise, $w_t$ is the measurement noise, and $\theta$ are the model parameters.

Fields

Dimensions

  • n_u::Int: input dimension
  • n_x::Int: state dimension
  • n_y::Int: output dimension
  • n_theta::Int: parameter dimension
  • n_v::Int: process noise dimension

Dynamics

  • f: state transition function
  • g: measurement function

Distributions (parameter-dependent)

Each of the following fields is a function that takes a parameter vector theta and returns the corresponding distribution, so that the distributions may depend on $\theta$:

  • get_dist_x0: distribution of the initial state $x_0$, i.e., $p(x_0 \mid \theta)$
  • get_dist_v: distribution of the process noise $v_t$
  • get_dist_w: distribution of the measurement noise $w_t$

Prior

  • dist_theta: prior distribution over the parameters $\theta$

Note

For any parameter vector $\theta$, the functions get_dist_x0(theta), get_dist_v(theta), and get_dist_w(theta) must return objects compatible with the Distributions.jl interface (i.e., supporting rand and logpdf).

PosteriorScenarioPlanning.simulate_trajectories — Function
simulate_trajectories(model, samples, u; rng, kwargs...)

Generate predictive state and output trajectories from posterior samples.

For each posterior sample, the model is simulated forward over the input trajectory u, producing one trajectory per sample. The result is an ensemble of trajectories representing posterior predictive uncertainty.

Arguments

  • model::AbstractModel: dynamics model
  • samples::Vector{<:AbstractPosteriorSample}: posterior samples
  • u::AbstractMatrix: input trajectory of size (n_u, n_t)

Keywords

  • rng::AbstractRNG: random number generator (default: Random.default_rng())
  • Model-specific noise realizations may be passed as additional keyword arguments (e.g. V, W for DiscreteTimeStochasticSSM). When provided, these are used directly instead of drawing fresh realizations from rng. When omitted or nothing, fresh noise is drawn. This allows callers such as solve_ocp! to produce initial guesses that are consistent with the noise realizations encoded in the OCP (see _extract_noise_values).

Returns

  • x::Array: state trajectories of size (n_x, n_t, K)
  • y::Array: output trajectories of size (n_y, n_t, K)

Notes

  • n_t is the number of time points; for an OCP with horizon H, n_t = H + 1.
  • K = length(samples) is the number of posterior samples.
  • Each slice x[:, :, k] and y[:, :, k] corresponds to posterior sample k.
  • Concrete model implementations must support passing pre-drawn noise realizations as keyword arguments. Any noise keyword that is nothing or omitted must be drawn internally using rng.

PosteriorScenarioPlanning.ParticleFilterBuffer — Type
ParticleFilterBuffer{FT,TX} <: AbstractBuffer

Pre-allocated storage used by the particle filter.

The buffer stores the particle states, normalized weights, ancestry indices, and temporary work arrays needed during propagation and weighting. It is designed to be reused across repeated particle filter evaluations in order to avoid repeated memory allocation.

Importantly, the buffer may be over-allocated: its capacity can exceed the number of particles N and time steps T used in a particular run. This allows reusing the same buffer without reallocation, e.g., when N is adapted.

Fields

  • x_pf::TX: Particle states over time; this is either a (T_max, N_max) matrix of SVector, or a (n_x, T_max, N_max) array of FT for the general case.
  • w_pf::Matrix{FT}: Normalized particle weights of size (T_max, N_max).
  • a_pf::Matrix{Int}: Ancestor indices of size (T_max, N_max).
  • log_w::Vector{FT}: Temporary storage for log weights at one time step.
  • v::Vector{FT}: Temporary storage for one sample of process noise.
  • N_max::Int: Maximum number of particles supported by this buffer.

PosteriorScenarioPlanning.ParticleMMHSampler — Type
ParticleMMHSampler{Mode,P} <: AbstractMHSampler

Particle Marginal Metropolis–Hastings (PMMH) sampler.

This sampler performs Bayesian inference for state-space models by embedding a particle filter within a Metropolis–Hastings scheme. The intractable likelihood $p(y \mid \theta)$ is replaced by an unbiased estimate obtained from the particle filter, ensuring that the Markov chain targets the correct posterior distribution.

Fields

  • proposal::P: proposal distribution used to generate candidate states
  • N::Int: number of particles used in the particle filter
  • mode::Mode: sampling mode (Standard or Blocked) determining the parameterization of the Markov chain

Modes

  • Standard: the proposal updates $\theta$ only; the initial state $x_0$ is sampled internally from $p(x_0 \mid \theta)$
  • Blocked: the proposal updates both $\theta$ and $x_0$

PosteriorScenarioPlanning.ParticleMMHState — Type
ParticleMMHState{FT} <: AbstractMCMCState

Internal state of the PMMH sampler in standard mode.

Fields

  • theta::Vector{FT}: current parameter vector $\theta$
  • log_likelihood::FT: estimated log-likelihood $\log p(y \mid \theta)$
  • log_prior::FT: log-prior value $\log p(\theta)$

  • Proposed states carry an empty (n_x, 0) placeholder until they are accepted (see accept_state!).

PosteriorScenarioPlanning.GaussianProposal — Type
GaussianProposal{FT} <: AbstractProposal

Symmetric Gaussian random-walk proposal for Metropolis–Hastings sampling.

Given a current parameter vector z, the proposal generates a candidate according to

\[z' = z + \varepsilon, \qquad \varepsilon \sim \mathcal{N}(0, \texttt{scale} \cdot \Sigma).\]

For blocked samplers, $z$ denotes the concatenated vector containing all proposed components, i.e., $z = [\theta; x_0]$.

Fields

  • Sigma::AbstractMatrix{FT}: base covariance matrix of the proposal
  • scale::FT: scalar multiplier applied to Sigma
source
PosteriorScenarioPlanning.PriorPredictiveSampler — Type
PriorPredictiveSampler <: AbstractMCMCSampler

Exact sampler for the prior of the parameters and latent states, propagated through the stochastic dynamics under the observed inputs.

Each call to mcmc_step! draws $\theta \sim p(\theta)$ and $x_0 \sim p(x_0 \mid \theta)$ and simulates the latent trajectory under the inputs of the data set with fresh process noise. The measurements are ignored. Consecutive draws are therefore independent and every step is accepted, so the sampler should be run without burn-in or thinning (MCMCConfig(0, 0)).

Notes

  • The samples are of type DiscreteTimeSSMSample{FT,Standard} and can be used wherever posterior samples of a ParticleMMHSampler are expected, e.g. as OCP scenarios or as validation scenarios of an AdaptiveCVaRPlanner.
  • Their log_likelihood is zero, as no measurements are conditioned on.

run_mcmc!(workspace, sampler, config, model, data, K)

Run a single MCMC chain using a pre-initialized workspace, collecting K samples.

The function advances the Markov chain in-place, performing burn-in, thinning, and sample collection. The chain dynamics (burn-in, thinning, step adaptations, verbosity) are taken from config; the number of samples K is a separate argument.   • config::MCMCConfig: chain dynamics (burn-in length, thinning interval, step adaptations, verbosity)

  • data::AbstractData: observed data

Returns

  • ChainResult with fields:
    • samples: vector of K posterior samples
    • acceptance_rate::Float64: ratio of accepted proposals over all iterations

Behavior

  • Performs MCMC transitions via mcmc_step!
  • Discards the first burnin iterations
  • Saves every (thinning + 1)-th sample thereafter
  • Applies StepAdaptations after each iteration

run_mcmc!(ensemble, config, model, data, K)

Run one MCMC chain per ensemble member, collecting K samples in total across all chains.

The requested count K is split as evenly as possible over the chains, with each chain collecting cld(K, n_chains) samples (ceiling division). When K is not a multiple of n_chains this rounds the total up, so slightly more than K samples may be returned. With more than one chain, the chains are run thread-parallel.

Arguments

  • ensemble::MCMCEnsemble: collection of chains to execute
  • config::MCMCConfig: chain dynamics (burn-in, thinning, step adaptations, verbosity)
  • model::AbstractModel: model under consideration
  • data::AbstractData: observed data
  • K::Int: total number of samples to collect across all chains

Returns

  • Vector{ChainResult}: one ChainResult per chain, each containing:
    • samples: posterior samples (cld(K, n_chains) per chain)
    • acceptance_rate: acceptance rate of the chain

Notes

  • The grand total cld(K, n_chains) * n_chains is ≥ K. Callers that need exactly K samples should flatten the per-chain results and take the first K.

PosteriorScenarioPlanning.RobbinsMonro — Type
RobbinsMonro{FT} <: AbstractStepAdaptation

Robbins–Monro step-size adaptation for the scale of a Gaussian proposal.

The adaptation updates the proposal scale in log-space at fixed batch intervals in order to steer the empirical acceptance rate toward a target value. If $\bar{\alpha}_k$ denotes the acceptance rate in batch $k$, the update is

\[\log(\sigma_{k+1}) = \log(\sigma_k) + \gamma_k (\bar{\alpha}_k - \alpha^*)\]

with gain sequence

\[\gamma_k = \frac{C}{k^{\kappa}}.\]

Fields

  • target_accept::FT: target acceptance rate $\alpha^*$
  • sub_chain_length::Int: number of MCMC iterations per adaptation batch
  • step_size_scale::FT: gain constant $C$
  • step_size_decay::FT: decay exponent $\kappa \in (0.5, 1]$
  • accepted_in_batch::Int: number of accepted proposals in the current batch
  • adaptation_count::Int: number of adaptation steps performed so far
  • verbose::Bool: if true, print diagnostics whenever an update is applied
source
PosteriorScenarioPlanning.NAdaptation — Type
NAdaptation <: StageAdaptation

Stage adaptation that adjusts the number of particles N in a particle filter based on an empirical estimate of the variance of the log-likelihood estimator.

The adaptation assumes the scaling relation

\[\mathrm{Var}(\log L) \approx C / N,\]

and selects N such that the variance matches a desired target level.

At each stage, the variance is estimated by repeatedly evaluating the log-likelihood at a subset of posterior samples using a fixed particle count. The resulting estimate is used to propose a new particle count, which is then clamped to [N_min, N_max].

Fields

  • N_min::Int: lower bound used when adapting N
  • N_max::Int: upper bound used when adapting N; also the maximum particle count that must be supported by the PF buffer
  • K_adapt::Int: number of posterior samples to evaluate variance at
  • N_adapt::Int: number of particles used in the variance-estimation PF runs
  • num_runs::Int: number of PF repeats per sample index
  • target_var::FT: target log-likelihood variance
  • verbose::Bool: if true, print adaptation details
source

PosteriorScenarioPlanning.compute_ess — Function
compute_ess(samples; max_lag=100)

Estimate the effective sample size (ESS) for each variable.

The ESS is computed as

\[ESS = \frac{K}{1 + 2 \sum_{l=1}^{\infty} \rho_l},\]

where $K$ is the total number of samples and $\rho_l$ is the autocorrelation at lag $l$. The sum is truncated at the first negative autocorrelation or at max_lag.

Arguments

  • samples::Vector{<:DiscreteTimeSSMSample}: posterior samples
  • max_lag::Int: maximum lag used in the autocorrelation sum

Returns

  • ess::Vector{FT}: ESS estimate for each variable

PosteriorScenarioPlanning.CVaRScenarioFormulation — Type
CVaRScenarioFormulation <: AbstractOCPFormulation

CVaR-penalized scenario optimal-control formulation.

This formulation computes a single input trajectory U that minimizes a combination of the sample-average cost across a set of scenarios and a Conditional Value-at-Risk (CVaR) penalty on the constraint values. Scenario constraints are not enforced as hard constraints; instead, their violations are penalized through the CVaR, so the problem remains feasible for any choice of the risk weight $\omega$.

Multi-dimensional constraints

For notational simplicity, the paper presents the CVaR formulation for a scalar constraint value $Z = h(\cdot)$. This implementation is the natural extension to $M$ scalar constraints $Z_1, \dots, Z_M$ (e.g., upper and lower bounds on states or outputs): the CVaR penalty is applied independently to each constraint dimension $Z_i$, introducing one auxiliary variable $\eta_i$ per dimension. This is preferred over aggregating constraints via $h = \max(h_1, \dots, h_M)$ because it avoids introducing a non-smooth operator into the NLP and allows the solver to penalize violations of individual constraints separately.

Mathematical formulation

For each scenario $k \in \{1, \dots, K\}$ the trajectory cost $J^{[k]}$ and the constraint value vector $Z^{[k]} \in \mathbb{R}^M$ are obtained by simulating the dynamics under the sampled parameters and disturbances. Following Rockafellar & Uryasev's CVaR reformulation, the resulting optimization problem is:

\[\begin{aligned} \min_{u_{0:H},\, \eta,\, s} \quad & (1 - \omega) \frac{1}{K} \sum_{k=1}^{K} J^{[k]} + \omega \sum_{i=1}^{M} \left( \eta_i + \frac{1}{\tau K} \sum_{k=1}^{K} s_{i,k} \right) \\ \mathrm{s.t.} \quad & x_{t+1}^{[k]} = f(x_t^{[k]}, u_t, v_t^{[k]}, \theta^{[k]}), \\ & y_t^{[k]} = g(x_t^{[k]}, u_t, \theta^{[k]}) + w_t^{[k]}, \\ & s_{i,k} \geq Z_i^{[k]} - \eta_i, \quad s_{i,k} \geq 0. \end{aligned}\]

The slack variables $s_{i,k}$ linearize the positive part $(Z_i^{[k]} - \eta_i)_+$.

Setting $\tau = \alpha$ aligns the CVaR risk measure with the desired robustness level; $\omega$ then trades off nominal performance against constraint satisfaction. It is equivalent to the penalty parametrization $\bar{J} + \lambda \, \mathrm{CVaR}$ under $\lambda = \omega/(1-\omega)$, but reaches pure CVaR minimization at the finite endpoint $\omega = 1$.

Fields

  • problem::OptimalControlProblem: problem definition containing cost, constraints, and prediction horizon

Notes

  • Input constraints are kept as hard constraints because they do not depend on the uncertainty and are always shared across scenarios.
  • Scenario constraints (both Box* and Functional* types) are converted to inequality expressions $Z_i^{[k]} \leq 0$ and CVaR-penalized; they are not added as hard constraints in this formulation.
  • $\omega = 0$ removes the CVaR term from the objective and leaves the auxiliaries $\eta_i$ unbounded along a ray of constant objective value, on which the interior-point barrier is unbounded below. Solve at a small positive $\omega$ instead of exactly zero if a pure-performance solution is needed.

PosteriorScenarioPlanning.RobustScenarioFormulation — Type
RobustScenarioFormulation <: AbstractOCPFormulation

Robust scenario optimal-control formulation.

This formulation computes a single input trajectory U that minimizes the worst-case cost across a set of scenarios (posterior samples), while enforcing dynamics and constraints for every scenario.

An epigraph reformulation is used, introducing an auxiliary variable $J_{\max}$:

\[\min_{u_{0:H},\; J_{\max}} \; J_{\max}\]

subject to, for all scenarios $k \in 1{:}K$:

\[\begin{aligned} x_0^{[k]} &= x_{\mathrm{current}}^{[k]}, \\ x_{t+1}^{[k]} &= f(x_t^{[k]}, u_t, v_t^{[k]}, \theta^{[k]}), \quad t \in 0{:}H{-}1, \\ y_t^{[k]} &= g(x_t^{[k]}, u_t, \theta^{[k]}) + w_t^{[k]}, \quad t \in 0{:}H, \\ J^{[k]} &= J(u_{0:H},\, x_{0:H}^{[k]},\, y_{0:H}^{[k]}) \leq J_{\max}, \\ h(&u_{0:H},\, x_{0:H}^{[k]},\, y_{0:H}^{[k]}) \leq 0. \end{aligned}\]

The input trajectory U is shared across all scenarios, while states $X^{[k]}$, outputs $Y^{[k]}$, and disturbances are scenario-specific.

When the problem uses WithoutOutputs, the output variables, observation constraints, and measurement-noise references are omitted entirely. In that case, cost functions and scenario constraints receive nothing in place of Y_k.

AbstractPlanner

Abstract supertype for planners that synthesize a certified input trajectory.

Whereas solve_ocp! performs a single optimization, a planner couples synthesis with a validation procedure and a scenario source. It repeatedly synthesizes and validates candidate inputs until the desired robustness guarantee is met or a retry budget is exhausted.

Concrete subtypes bundle the components they orchestrate (e.g. an OCP workspace, a sampler for drawing fresh validation scenarios, and a calibration configuration) and implement plan!.

PosteriorScenarioPlanning.plan! — Function
plan!(planner::AbstractPlanner, model, data; kwargs...)

Run a planner's synthesis–certification procedure and return its result.

In contrast to solve_ocp!, which solves a single optimization problem, plan! drives the full adaptive procedure: synthesizing candidate inputs, validating them on freshly drawn scenarios, and adjusting the formulation parameters until a robustness guarantee is achieved or the retry budget is exhausted.

Arguments

  • planner::AbstractPlanner: planner bundling an optimization engine, a validation procedure, and a scenario source
  • model::AbstractModel: prediction/inference model
  • data::AbstractData: current data

Returns

  • a planner-specific result describing the validated candidate (or the best candidate found) together with the achieved guarantee

PosteriorScenarioPlanning.AdaptiveCalibrationConfig — Type
AdaptiveCalibrationConfig

Configuration of the adaptive CVaR calibration procedure.

This struct holds the parameters of the adaptive calibration procedure — the risk and confidence targets, the $\omega$ update, and the validation loop. The OCP engine and sampler are held by AdaptiveCVaRPlanner.

The procedure adjusts a candidate's risk weight until its certified risk bound $\delta$ — an upper bound on the constraint-violation probability, obtained from the validation step — falls into the acceptance band below the target risk level $\alpha$.

Fields

Risk and confidence targets

  • alpha::FT: risk level $\alpha$. A solution is certified when $\delta \leq \alpha$, i.e., the realized trajectory satisfies the constraints with probability at least $1 - \alpha$.
  • alpha_tol::FT: width of the acceptance band below $\alpha$. The search stops when $\delta \in [\alpha - \alpha_{\mathrm{tol}}, \alpha]$. Solutions with $\delta < \alpha - \alpha_{\mathrm{tol}}$ are considered too conservative.
  • beta::FT: overall confidence level $\beta$. The certification holds with confidence at least $1 - \beta$ across the whole procedure.
  • n_max::Int: maximum number of synthesis–validation attempts. Also acts as an infeasibility detector: if no candidate is certified within n_max attempts, the posterior uncertainty is likely too large for the desired robustness level.
  • K_val::Int: number of validation scenarios drawn per attempt

Update law

  • omega_init::FT: risk weight $\omega_1$ of the first attempt of every cycle, unless overridden by the omega_init keyword of plan!
  • omega_min::FT: lower floor $\omega_{\mathrm{min}} \in (0, \omega_1)$ on the risk weight. The secant never proposes a smaller value, and an attempt at the floor that is certified but below the acceptance band terminates the cycle, since lowering $\omega$ further cannot reduce conservatism.
  • s_init::FT: initial elasticity $s_{\mathrm{init}} < 0$, used for the first step and whenever the cycle has not yet produced a well-conditioned fit, unless overridden by the s_init keyword of plan!
  • s_flat::FT: upper limit $s_{\mathrm{flat}} < 0$ on the elasticity. Every fitted slope above it (including any positive one) is capped there, which bounds the resulting step from the slope side.
  • step_bounds::Tuple{FT,FT}: minimum and maximum magnitude of the step in $x = \log\lambda$, i.e. the multiplicative bounds on the factor by which $\lambda$ may change per attempt. The direction is set by the sign of the miss, so the same bounds guard steps in both directions.
  • margin_fraction::FT: fraction $m \in [0, 1)$ by which the target violation rate is set below the largest certifiable one, $p^* = (1 - m) \, p^*_\alpha$
  • n_recovery::Int: number of final attempts given to the recovery phase, active only while no candidate has certified. Zero disables the phase, leaving the search entirely to the secant.
  • gamma_decay::FT: recency weighting $\gamma \in (0, 1]$ of the elasticity fit; $\gamma = 1$ is an unweighted fit over the non-recovery attempts of the cycle.
  • min_spread::FT: minimum weighted spread of the abscissae $x$ below which the elasticity fit is considered ill-conditioned

Notes

  • The confidence is split uniformly via a Bonferroni correction, $\beta_{\mathrm{att}} = \beta / n_{\mathrm{max}}$, to maintain the overall confidence $1 - \beta$ under repeated testing.
  • The acceptance band must be non-empty and contained in $[0, \alpha]$; this is enforced by the inner constructor.

PosteriorScenarioPlanning.AdaptiveCVaRPlanner — Type
AdaptiveCVaRPlanner{P,E,FT} <: AbstractPlanner

Closed-loop planner that produces a certified input trajectory by adaptively calibrating the CVaR risk weight $\omega$.

The planner bundles the components of the synthesis–validation loop:

  • a CVaR-penalized scenario OCP,
  • a warm MCMC ensemble that supplies fresh validation sets,
  • the calibration configuration, and
  • the per-cycle history the elasticity is estimated from.

Calling plan! repeatedly solves the OCP for the current $\omega$, certifies the candidate on a freshly drawn validation set via clopper_pearson_bound, and accepts as soon as the certified bound $\delta$ enters the acceptance band $[\alpha - \alpha_{\mathrm{tol}}, \alpha]$; otherwise $\omega$ is moved toward the target violation rate and the OCP is resolved.

Fields

  • ocp_workspace::P: CVaR scenario OCP workspace (CVaRScenarioWorkspace) holding the training scenarios. Its $\omega$ parameter is updated in place across attempts while the training scenarios are held fixed.
  • ensemble::E: warm MCMC chains (MCMCEnsemble) continued in place to draw a fresh, independent validation set of config.K_val scenarios each attempt
  • sampler_config::MCMCConfig: chain dynamics (thinning, burn-in, …) used when drawing validation samples
  • config::AdaptiveCalibrationConfig{FT}: calibration configuration
  • history::CalibrationHistory{FT}: preallocated per-cycle history, reset by every call to plan!

Notes

  • The Clopper–Pearson certification requires the validation scenarios to be drawn independently of the training scenarios baked into ocp_workspace; the validation set must not reuse or overlap with them. This statistical independence is unrelated to the number of chains in ensemble, which does not need to match config.K_val.

PosteriorScenarioPlanning.AdaptiveCVaRResult — Type
AdaptiveCVaRResult{FT,S}

Result of an adaptive calibration run produced by plan!.

Fields

  • solution::OCPSolution{FT}: the returned candidate solution, however the calibration ended: the certified candidate with the lowest validation cost if any attempt met $\delta \leq \alpha$, otherwise the one with the smallest observed $\delta$.
  • delta::Float64: certified violation-probability bound $\delta$ of solution (computed at confidence $\beta_{\mathrm{att}} = \beta / n_{\mathrm{max}}$)
  • beta::Float64: overall confidence level $\beta$ the bound was computed against
  • omega::Float64: risk weight $\omega$ that produced solution
  • cost::Float64: sample-average cost of solution on its validation set
  • certified::Bool: true if the returned solution meets the hard requirement $\delta \leq \alpha$; false otherwise.
  • attempts::Int: number of synthesis–validation attempts performed
  • termination::Symbol: how the calibration ended — :in_band (an attempt landed in the acceptance band), :floor (an attempt at $\omega \leq \omega_{\mathrm{min}}$ was below the band), or :exhausted (all n_max attempts were used without landing in the band; certified tells whether the returned candidate meets $\delta \leq \alpha$)
  • runtime_optimization::Float64: total wall-clock time (s) spent in the OCP solves (solve_ocp!) across all attempts
  • runtime_validation::Float64: total wall-clock time (s) spent drawing validation scenarios, counting violations, and evaluating the validation cost across all attempts
  • delta_history::Vector{Float64}: the bound $\delta$ observed at each attempt
  • violation_history::Vector{Int}: the validation violation count $V$ at each attempt
  • omega_history::Vector{Float64}: the risk weight $\omega$ used at each attempt
  • cost_history::Vector{Float64}: the sample-average validation cost of the candidate at each attempt
  • update_history::Vector{CalibrationStep}: diagnostics of each risk-weight update
  • U_history::Vector{Matrix{FT}}: the candidate input trajectory synthesized at each attempt, e.g., to compare the first and the returned candidate
  • validation_scenarios::Vector{S}: the K_val validation scenarios drawn in the last attempt. They are drawn independently of every candidate, unlike the training scenarios the candidates were optimized on, and so give an unbiased view of a candidate's predictive distribution.

PosteriorScenarioPlanning.CalibrationHistory — Type
CalibrationHistory{FT}

Within-cycle record of the failed calibration attempts, in the coordinates the elasticity is fitted in.

One calibration cycle is one call to plan!. The history is preallocated to n_max entries at planner construction and reset at the start of every cycle, so a receding-horizon loop reuses the same storage without accumulating points across time steps — the response curve moves as the posterior and the initial condition change, and stale points would bias the fit.

Fields

  • x::Vector{FT}: abscissae $x_j = \mathrm{logit}(\omega_j) = \log\lambda_j$
  • y::Vector{FT}: ordinates $y_j = \log(V_j / K_{\mathrm{val}})$, the log empirical violation rate
  • n::Int: number of valid entries; x and y are only meaningful up to n
  • s_init::FT: initial elasticity of the current cycle, used until the cycle has produced a well-conditioned fit; set by plan!
  • last_slope::FT: elasticity applied by the most recent update of this cycle, or NaN before the first one. An ill-conditioned fit is not evidence that the response changed, so the update reuses this value rather than discarding what the cycle has already measured.

PosteriorScenarioPlanning.CalibrationStep — Type
CalibrationStep

Diagnostics of one risk-weight update, recorded per attempt by plan!.

Both the raw and the guarded quantities are kept: a run in which the ceiling binds often indicates that the elasticity estimate is unreliable or that s_init is badly off, which cannot be seen from the post-clip values alone.

Fields

  • omega::Float64: risk weight $\omega_j$ the attempt was solved at
  • slope_raw::Float64: elasticity from the weighted fit, NaN when fewer than two points were available
  • slope::Float64: elasticity actually used — the fit, its cap at s_flat, the one last applied, or s_init (see slope_source)
  • spread::Float64: weighted spread of the abscissae the fit was based on
  • step_raw::Float64: secant step $\Delta$ before clipping; negative when the attempt overshot into over-conservatism
  • step::Float64: step actually taken in $x$: the secant step with its magnitude clipped to step_bounds and the sign of step_raw preserved, the largest admissible step after a saturated attempt, or the step to the bracket midpoint (see clip)
  • omega_lo::Float64: lower end of the bracket, a risk weight with too many violations (see bracket_source); NaN if no usable bracket exists
  • omega_hi::Float64: upper end of the bracket, a risk weight with too few violations (see bracket_source); NaN if no usable bracket exists
  • bracket_source::Symbol: which attempts the bracket was built from — :extremes (the largest ω with too many and the smallest with too few violations), :recent (the most recent attempt on each side, used when the extremes are inconsistent), or :none (no usable bracket)
  • omega_secant::Float64: risk weight proposed by the secant step, after bracketing
  • omega_recovery::Float64: risk weight proposed by the recovery phase; equal to omega while the phase is inactive
  • recovery_active::Bool: whether the recovery phase was in force
  • omega_next::Float64: risk weight of the following attempt
  • slope_source::Symbol: where the applied elasticity came from — :measured, :capped, :reused, or :init
  • clip::Symbol: which rule set the step — :none (the plain secant step), :floor or :ceiling (its magnitude was clipped), :saturated (the attempt was saturated and the largest admissible step was taken), or :bisected (the step would not have landed at least step_bounds[1] inside the bracket, and its midpoint was taken instead)
